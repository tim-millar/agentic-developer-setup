# Local agent run reporting

Run the Ruby reporter from a framework checkout.

```sh
ruby scripts/report_agent_runs.rb
ruby scripts/report_agent_runs.rb \
  --telemetry-dir /absolute/path/to/runs \
  --repository example-owner/example-repo \
  --as-of 2026-04-01T00:00:00Z \
  --output /absolute/path/to/ads-baseline.md
```

Without a root argument, the reporter selects the same local storage as the launchers: nonempty `AGENT_TELEMETRY_DIR`, then nonempty `XDG_DATA_HOME`, then `$HOME/.local/share`. The latter two locations use the suffix `agent-development-framework/telemetry/runs`. A missing implicit root yields an empty report. An explicit root must be an existing readable absolute directory. The report identifies the scope and includes a SHA-256 digest of the canonical root path for local reference. This digest identifies the location. To identify a particular snapshot, record a separate evidence manifest as described below.

The optional repository filter compares GitHub identities case-insensitively. Local path-digest identities are counted in unfiltered activity and are ineligible for GitHub PR metrics. Output goes to standard output by default. `--output` takes an absolute path with an existing parent directory and replaces a regular report atomically outside telemetry storage. A report written by the command has private permissions. Shell redirection is handled by the shell, so use `--output` when you want the command to check the destination.

The command returns 0 for a generated report, including an empty corpus. Invalid arguments return 2 and print usage. A root or output error returns 1. Malformed records appear in the report diagnostics and leave unrelated evidence usable.

## Sources and scope

The reporter reuses the v1 validators for [execution](run-telemetry.md), [provider usage](run-usage.md) and [outcomes](run-outcomes.md). The unit of run activity is a valid `run.json` whose `run_id` matches its canonical run directory. A resume is a separate run even if it uses a previous provider session. A sidecar must validate and join by the same ID. An invalid optional sidecar leaves the base run and any other valid sidecar usable. The reporter lists invalid canonical run entries before applying the repository filter since a rejected record may have no reliable repository identity. Unrelated directory names are ignored. Run directories and evidence files reached through symlinks inside the root are skipped.

The utility reads the three JSON records and the bundled usage schema. It leaves telemetry and repository state untouched and works offline. Task snapshots, provider session storage and credentials are outside its input. The resulting aggregate may contain private repository and model identifiers. Store operational reports and manifests locally.

## Metric catalogue

| Metric | Source, unit and eligibility | Coverage and interpretation |
| --- | --- | --- |
| Recorded runs | Valid v1 `run.json`, one per `run_id`. Includes started, failed and interrupted invocations. | All valid in-scope runs. Invalid canonical entries are excluded and counted separately. |
| Usage coverage | Run-level `usage.collection.state`: complete, partial, unavailable, disabled, absent, or invalid/unsupported. | Percentage is complete sidecars divided by all in-scope runs. Absence and failure convey no numeric measurements. |
| Outcome coverage | Run-level `outcome.reconciliation.observation_state`: complete, partial, unavailable, not applicable, absent, or invalid/unsupported. | Usable coverage is complete or partial divided by runs with applicable GitHub identities. The report excludes valid not-applicable outcomes from that denominator and counts unavailable, absent and invalid outcomes for applicable runs. |
| Outcome correlation | Run-level `outcome.correlation.state`: matched, unmatched, ambiguous, unavailable, or not applicable. Absent and rejected sidecars have separate rows. | A complete reconciliation can be unmatched. Candidates contribute no PRs. |
| Run activity | Runs by `state`, `runtime.client.id`, `repository.identity` and UTC month of `timing.run_started_at`. | Each breakdown counts invocations. Events that cross a month boundary stay in the start month. A schema-shaped start timestamp that cannot be interpreted as a real UTC date appears in the unknown cohort. |
| Observed models | Exact `measurements[].provider` and `model` in complete or partial usage. Shows run incidence and successful-response measurements per provider/model and collection state. | One run can appear for several models. Reported configuration from `run.json` contributes no model usage. Missing collection leaves model activity unknown. |
| Successful-response measurement count | `usage.observed_totals.measurement_count`, summed over eligible complete or partial run sidecars separately. | A complete record can establish zero. An empty eligible population has an unavailable count. |
| Input and output token dimensions | `observed_totals.input_total`, `input_uncached`, `input_cache_read`, `input_cache_write`, `output_total`, and `output_reasoning`, summed for complete and partial collection separately. The model breakdown uses the corresponding `measurements[].tokens` fields. | Each dimension shows contributing runs or measurements out of its population. Nulls do not contribute. Run totals require the sidecar to establish that dimension for the entire run. Model subtotals use measurements with established values. Cache writes remain separate from uncached input normalization. Reasoning is already included in output. |
| Cache-read percentage | `measurements[].tokens.input_cache_read` divided by `input_total`, using the sums over a common eligible measurement population. | Each eligible pair has both dimensions, positive total input and read input no greater than total. The sidecar can retain a flagged inconsistent partial pair, which is omitted from this ratio. The report shows paired measurement coverage and an unavailable percentage for zero eligible input. |
| Runtime monetary evidence | Valid `cost_summary.state`, `semantics`, `currency`, `observed_usd_micros`, `priced_measurement_count` and `measurement_count`. Amounts are grouped by state, semantic and currency. | Each amount has a contributing run and priced/recorded measurement count. Global price coverage includes unpriced observed measurements. Unavailable cost remains unknown. The supported `runtime_estimated` USD figures are provider estimates. |
| Distinct associated PRs | `outcome.correlation.associations` for matched runs, deduplicated by case-insensitive repository and PR number. A PR can be linked to several runs and a run can be linked to several PRs. | Reports the count of confirmed links and of runs with at least one link to the PR population. A confirmed PR can have no reliable current details. Each run's usage is aggregated once, independent of its PR associations. |
| PR lifecycle | `pull_requests[].current.lifecycle`, one per confirmed PR, from the most recent reliable `current.observed_at`. | Counts open, merged, closed unmerged and unavailable/conflicting. A newer details placeholder does not replace a reliable snapshot. Equal-time disagreement about an observed field leaves that field unavailable and produces a conflict diagnostic. |
| Reviewed-revision evidence | `derived.reviewed_revision_count` on the most recently reconciled observation of a confirmed PR, using `last_successful_at` with `current.observed_at` as a fallback. `reviews[]` determines whether commit identities are missing. | Counts distinct reliable reviewed commits under the outcome contract. Reports a distribution for usable evidence, a separate count of PRs with complete evidence and no submitted review, and incomplete/unavailable evidence. Retained positive counts can also be incomplete. A missing commit ID never creates a revision. Partial reconciliation alone cannot establish an absence of reviews. |
| Post-first-review change | `derived.post_first_review_change_observed` from the same reconciliation selection, one per confirmed PR. | Displays yes, no, unavailable and not applicable separately. Conflicting equal-time values appear as unavailable. A reported change does not establish reviewer causation. |
| Creation-to-merge interval | `current.merged_at - current.created_at` from the reliable current observation of each merged PR. | Only nonnegative intervals with both reliable timestamps contribute. Reports eligible n out of merged PRs, median, minimum, maximum and the excluded count. An empty population has unavailable statistics. This is calendar time, including wait time. |
| Reconciliation observation time | Latest usable `reconciliation.last_successful_at` among in-scope complete or partial outcomes. | Unavailable when no valid timestamp is present. A failed attempt's timestamp does not advance this measure. |
| Monthly cohorts | Run-start month for activity, usage coverage and resources. PR-creation month from `current.created_at` for lifecycle, reviews and intervals. | Each series includes empty intermediate months between its first and last dated cohorts. PRs with missing or conflicting creation timestamps use an unknown cohort. Dated PR cohorts show maturity relative to the end of the UTC creation month. Zero recorded activity only describes the selected corpus. |

For a fixed source snapshot and options, use the same `--as-of` value to reproduce the report byte for byte. The default is the current UTC time. The timestamp sets the report date and cohort maturity. The report uses evidence in the supplied snapshot even when a reconciliation happened after `--as-of`. A later reconciliation can change `outcome.json` and the next report even if `run.json` and `usage.json` stay fixed.

Compare months with care. Recent PR cohorts have had less time for reviews and merges. Task complexity, model selection, repository differences, workflow changes and evidence completeness can all affect differences between cohorts. The metrics describe observed activity, resource evidence and GitHub state. They cannot establish implementation acceptance, quality, model effectiveness or developer productivity.

## Preserve and verify an initial baseline

1. Select the existing run directory using the storage precedence above. Choose a local report directory outside both telemetry and the public checkout.
2. Generate a report against the selected root with an explicit UTC timestamp. Start with all repositories for the overall baseline. The report lists invalid or unreadable records while retaining the usable corpus.
3. Review missing and partial coverage, invalid files, PR conflicts, unknown creation dates and unavailable cost. For an interim report, annotate the reconciliation gaps locally and refresh the engineering-outcome baseline after [#90 recovery](https://github.com/tim-millar/agentic-developer-setup/issues/90) has been verified.
4. Check the run total against the canonical run directories containing `run.json`. Compare any difference with the rejected-entry diagnostics. If filtered, count only validated matching GitHub identities. Use `ruby scripts/validate_run_telemetry.rb /absolute/path/to/run.json` for a sample or each disputed record.
5. Spot-check several complete and partial `usage.json` sidecars with `ruby scripts/validate_run_usage.rb /absolute/path/to/usage.json`. Compare summed `observed_totals` for the same eligible records, then verify a model split, paired-token ratio and any available priced-measurement coverage. Include a sidecar with an unavailable dimension in the check.
6. Spot-check matched `outcome.json` sidecars with `ruby scripts/validate_agent_run_outcome.rb /absolute/path/to/outcome.json`. Compare confirmed repository/PR pairs across runs, inspect the latest reliable current snapshot and verify the PR appears once in its UTC creation cohort. Compare a review count and a merge interval with their source fields.
7. Save the Markdown, the report options and timestamp, recorded period, and known gaps in local storage. Save a manifest of the canonical run IDs and checksums of their three JSON files, or keep a private copy of just those JSON files in their run directories if exact reproduction is needed. Capture during a quiet period or verify the manifest before and after generation to detect updates during the read. A location digest alone does not capture changes to the evidence. Keep the report, manifest and source data out of the public repository and any automatic uploads.
8. Record the questions that remain unsupported by the evidence, such as billed cost, effort spent waiting versus working, implementation acceptance and causal comparisons between models or months.
